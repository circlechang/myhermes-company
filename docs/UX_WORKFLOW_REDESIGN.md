# 工作流重設計（IDEO 視角）— 提案

日期：2026-09-02　狀態：提案，未實作

## 一、觀察：混亂從哪裡來

盤點現況（mock 截圖＋程式碼）：

| 層面 | 現況 | 數量 |
|---|---|---|
| 站的種類 | AI 員工／跑程式／等我確認／看情況分岔／重複直到／送出結果 | 6 |
| 一張站卡露出的欄位 | 標題、誰做、做什麼、產出、完成條件（自檢）、這一站的產出、試跑、刪除、拖曳把手、狀態籤 | 10 |
| 站與站之間 | 「帶著：文字輸出」標籤＋「在這裡插一站」 | 2 |
| ⋯ 選單 | 進階檢視、排程、webhook、預算、匯出、歷史 | 6 |
| 相關頁面 | 清單、編輯器（站／畫布兩種）、執行頁（快照回放）、審批頁、收件匣、今天 | 6 |
| 詞彙 | 工作流、產線、站、節點、執行、重跑、試跑、快照、回放、閘門、審批、核准、退回、完成條件、自檢、done_check、預算、budget_exceeded、觸發、排程、webhook、進階檢視 | 22 |

三個根本問題：

1. **兩套心智模型打架**。「產線／站」是給老闆看的線性故事，「節點／邊／畫布」是工程師的 DAG。分岔和迴圈這兩種站，提示文字自己就寫「接線要用進階檢視」，代表它們不屬於簡單模式，卻放在同一個選單裡。
2. **每張站卡都是編輯模式**。三站就佔三個螢幕，因為每張卡永遠展開 textarea 和五個欄位。老闆打開一條線，九成時間是「看上次跑得怎樣」，不是改 prompt。
3. **「工作流」本身就是軟體詞**。老闆腦中的東西是：「每天早上八點，研究員找三個熱點，我挑一個，小編寫貼文，發到 LINE」。那是一條**交辦鏈**：誰 → 做什麼 → 交給誰 → 哪裡停下來等我 → 什麼時候跑 → 結果送去哪。六個問題，沒有一個叫 node。

## 二、重新定義問題

**不是**「怎麼把 DAG 編輯器做得好用」。
**而是**「怎麼讓一個人用一句話交辦一件會重複發生的事，然後看得懂結果」。

條件 → 機制 → 結果：老闆會描述流程但不會畫圖 → 介面用「交辦鏈」的六個問題當骨架、系統詞全部往後藏 → 三站流程從三個螢幕縮成一眼看完，出錯時一眼看到卡在哪。

## 三、設計原則

1. **一句話開始，不從零件開始**。建立流程的第一步是打一句話（或選範本），AI 員工先排出草稿鏈，人再調。不是先選站種類。
2. **閱讀模式是預設，編輯是例外**。站卡收起來只有一行：「研究員 · 找出今天三個熱點」。點了才展開。
3. **只有三種動作**：請員工做、等我看、送出去。「跑程式」併入「請員工做」（員工本來就有 runtime 屬性，devbot 就是 Claude Code）。分岔、迴圈、自檢、預算、webhook、畫布、快照回放 → 工程師模式才出現。
4. **打開一條流程，先看上次結果**。預設落在「最近一次」：每站一行狀態＋一行結果摘要；改設定是第二個分頁。
5. **一個地方等我**。審批不再是獨立頁；卡在哪站就在那站，今天頁和收件匣是入口。
6. **詞彙換成公司用語**。

| 現在 | 改成 | 理由 |
|---|---|---|
| 工作流 | 流程 | 中文本來就有的詞 |
| 站／節點 | 站 | 只留一個 |
| 執行／run | 跑一次／這一次 | 動詞化 |
| 重跑這一站 | 從這站再跑 | 說清楚會往下跑 |
| 閘門／審批／核准／退回 | 等我看／可以／退回 | 老闆不「核准」自己的員工 |
| 完成條件（自檢） | 隱藏；工程師模式叫「做完自己檢查」 | 老闆不會知道要不要勾 |
| 帶著：文字輸出 | 拿掉，只留箭頭 | 每條線都一樣，沒有資訊量 |
| 觸發／排程／webhook | 什麼時候跑 | 一個問題 |
| 預算 | 最多花多少 | |
| 進階檢視 | 工程師模式：畫布 | |
| 快照回放 | 工程師模式：逐步回放 | |

## 四、畫面草圖

**流程清單**（取代現在的表格）

```
每日熱點內容產線                     研究員 → 你 → 小編 → LINE
上次：今早 08:00 ✓ 完成（花 $0.41）  下次：明早 08:00        [跑一次]

PPWR 週報                            資料員 → 主編 → 檔案
上次：週一 ⚠ 第 2 站失敗：LINE 未設定                        [跑一次]
```
每列回答：誰參與、上次怎樣、下次何時、要不要現在跑。匯入 JSON、批次刪除、profile 篩選 → ⋯。

**流程頁，預設分頁「最近一次」**

```
每日熱點內容產線                                    [跑一次] [⋯]
今早 08:00 開始 · 08:04 完成 · $0.41

① 研究員  找出今天三個熱點                  ✓ 3 分鐘   「一、PPWR 授權代表新規…」
② 你      挑一個                            ✓ 你選了第一題（08:02）
③ 小編    依選題寫 LINE 貼文                 ✓ 40 秒    「【PPWR 新規】從 11/12 起…」
④ 送到    LINE 群「行銷組」                  ✓ 已送出

[看完整產出]   [之前跑過的 12 次 ▾]
```

**分頁「怎麼跑」**（就是現在的站卡，但收起來）

```
① 研究員 · 找出今天三個熱點                          [試跑]  ▸
② 等我看                                                     ▸
③ 小編 · 依選題寫 LINE 貼文                          [試跑]  ▸
④ 送到 LINE · 行銷組                                         ▸
                                          + 加一步（請員工做／等我看／送出去）

什麼時候跑：每天 08:00 ▾      最多花多少：$1 ▾
```
點一步才展開「誰做／做什麼」兩個欄位，其他都在工程師模式。

**建立流程**

```
描述這件事，越像交代同事越好：
┌──────────────────────────────────────────────────────────┐
│ 每天早上找三個循環包裝的熱點，我挑一個，小編寫成 LINE 貼文發到行銷組 │
└──────────────────────────────────────────────────────────┘
                                   [幫我排成流程]   或選範本 ▾
```
AI 員工吐出四步草稿，人在「怎麼跑」分頁裡調。範本保留，放第二順位。

## 五、邊界：什麼時候線性模型不夠

- 行銷套件的 fanout／select（一稿分三版、閘門選一版）需要分岔。這是真需求，但是套件作者的需求，不是老闆每天碰的。放工程師模式的畫布，套件裝好後在「最近一次」分頁照樣以線性方式讀（分岔站顯示「三版 → 選了 B」一行）。
- 迴圈（重複直到）目前沒有範本用到。先藏。
- 條件分岔用規則（regex／json_path）的，老闆一定看不懂；工程師模式限定。

## 六、驗證方式

找兩個沒看過這系統的人，各做三件事，計時、數走錯的點擊：

1. 建一條「每天找熱點、我確認、小編寫貼文」並跑一次。
2. 上次跑失敗了，找出哪一站、為什麼。
3. 把第二站換成另一位員工，從那站再跑。

我預測現況會卡在：完成條件那個勾、「帶著」標籤、在 ⋯ 裡找排程、跑完要往右邊的產出欄看。重設計後三件事都應該在 2 分鐘內、零次進 ⋯。

## 七、分期

- **第一期（一天）**：站卡閱讀模式＋點開編輯、三種動作、清單卡片化、詞彙表、分岔／迴圈／自檢／畫布／回放收進工程師模式、審批頁從側欄拿掉。不動後端。
- **第二期（半天）**：流程頁預設「最近一次」分頁；「什麼時候跑／最多花多少」搬到怎麼跑分頁底部。
- **第三期（一天）**：一句話建流程：`POST /workflows/draft {text}` 用 Hermes 員工排草稿鏈。
